# Smart Clinic Management System – Architecture Design

## Section 1: Architecture Summary

The Smart Clinic Management System is built on a **three-tier architecture** that separates the application into three distinct layers: Presentation, Application, and Data. The **Presentation Tier** serves two types of consumers: server-rendered HTML dashboards built with **Thymeleaf** (Admin Dashboard and Doctor Dashboard), and external clients (mobile apps, SPAs, third-party services) that consume **RESTful APIs** returning JSON for modules such as appointments, patient panel, and patient records. The **Application Tier** is a **Spring Boot** backend that hosts both **MVC controllers** (for Thymeleaf views) and **REST controllers** (for JSON endpoints), a **service layer** that enforces business rules and coordinates workflows, and a **repository layer** that abstracts data access. Security is enforced through **Spring Security + JWT**, so both dashboards and APIs share the same authentication mechanism. The **Data Tier** is polyglot: **MySQL** stores structured, transactional data (Patient, Doctor, Appointment, Admin) accessed through **Spring Data JPA / Hibernate**, while **MongoDB** stores flexible, document-oriented data (Prescription and other unstructured clinical records) accessed through **Spring Data MongoDB**. This three-tier design improves scalability, maintainability, and deployment flexibility because each layer can be developed, tested, or scaled independently. The application is packaged with **Docker** for cloud-native deployment and integrates with **CI/CD pipelines** (GitHub Actions) for automated builds, tests, and releases.

## Section 2: Numbered Flow – Request/Response Cycle

1. **User interaction (Presentation Tier)** – A user accesses the system either through a Thymeleaf-rendered page (Admin Dashboard, Doctor Dashboard) in the browser, or through a REST client (mobile app, SPA) that calls a JSON endpoint such as `GET /api/appointments`.
2. **Controller Layer** – The request is routed based on URL and HTTP method. Server-rendered view requests are handled by Thymeleaf controllers that return `.html` templates; API requests are handled by `@RestController` classes that produce JSON.
3. **Service Layer** – All controllers delegate to the service layer, which applies business rules and validations, coordinates workflows across entities (e.g., checking doctor availability before scheduling an appointment), and keeps controllers free of data-access logic.
4. **Repository Layer** – The service layer calls the appropriate repository: Spring Data JPA repositories for relational data (Patient, Doctor, Appointment, Admin), and Spring Data MongoDB repositories for document data (Prescription).
5. **Database Access** – Each repository talks to its underlying engine. MySQL stores normalized relational entities with constraints; MongoDB stores flexible, nested documents that can evolve without migrations.
6. **Model Binding** – Retrieved data is mapped back to Java objects: JPA entities (`@Entity`) for MySQL rows, and document objects (`@Document`) for MongoDB collections.
7. **Response Layer** – In MVC flows, models are passed from the controller to Thymeleaf templates and rendered as dynamic HTML. In REST flows, the same models (or transformed DTOs) are serialized into JSON and returned as an HTTP response. This completes the request-response cycle, delivering either a full web page or structured API data depending on the consumer.
